Dialogflow CX vs ES: What 3 Years of Testing Taught Me

When CX shines, when ES is enough, and what the documentation doesn't tell you about multilingual conversational flows.

I've spent the better part of three years testing conversational AI platforms at EXL, and no question comes up more often than this: should we use Dialogflow ES or Dialogflow CX? The answer, unsurprisingly, is "it depends" — but after hundreds of test cycles across both platforms, I can tell you exactly what it depends on.

The fundamental difference

ES (Essentials) is intent-based. You define intents, map training phrases to them, and the engine matches user input to the best intent. It's linear, predictable, and easy to reason about. CX is flow-based. You design conversation flows as state machines with pages, transitions, and route groups. It's more powerful — and more complex.

The complexity difference matters enormously for testing. An ES agent with 50 intents has a relatively bounded test surface. A CX agent with 20 flows, each containing multiple pages with conditional transitions, has a combinatorial explosion of possible paths. Your test strategy needs to account for this.

Where ES wins

For simple, single-turn interactions — FAQs, basic command-and-response bots, quick lookup assistants — ES is not just sufficient, it's preferable. The testing overhead is lower, the debugging is simpler, and the intent confidence scores are transparent and easy to validate.

ES also has an edge in rapid prototyping. When a product team comes to us with "we need a chatbot for X by next sprint," ES gets us to a testable prototype faster. We can validate the core intent matching, refine training phrases, and have a quality baseline within days.

Where CX is non-negotiable

The moment your conversation requires multi-turn context, branching logic, or complex entity handling across turns, CX becomes necessary. Here's what I mean:

  • Multi-turn booking flows. A hotel booking that asks for dates, room type, guest count, and payment — each depending on previous answers. ES can technically do this with contexts, but it becomes a maintenance nightmare.
  • Multilingual support at scale. CX's language-per-flow architecture is significantly cleaner to test than ES's approach. We can isolate language-specific test suites per flow without cross-contamination.
  • Webhook orchestration. When a single conversation turn requires multiple backend calls with conditional logic between them, CX's fulfillment model is far more testable.

What the docs don't tell you

Here are the testing pain points I've discovered that you won't find in Google's documentation:

CX's transition routes can create silent failures. If a page transition condition is met but the target page has no entry fulfillment, the user gets a blank response. This isn't flagged as an error anywhere. You have to test for it explicitly by mapping every transition and verifying that every target page has a meaningful response.

ES intent priority is fragile. Adding a new intent can quietly steal matches from existing intents if the training phrases overlap. We run regression tests on intent matching after every addition — a step that most teams skip and later regret.

Multilingual CX agents need per-language testing, not translated testing. Running your English test suite through Google Translate and calling it multilingual testing is a recipe for missed bugs. Language-specific intents, entity handling, and cultural context all need dedicated test scenarios.

My recommendation

Start with ES unless you have a clear reason for CX. The testing overhead of CX is substantial, and if your use case doesn't require multi-turn flows, that overhead is pure waste. But when you need CX, commit to it fully — including the testing investment. Half-measured CX testing is worse than none, because it gives you false confidence.

The best platform is the one your team can test thoroughly. An untestable CX agent is more dangerous than a well-tested ES bot.
